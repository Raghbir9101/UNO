2026-08-05 — Fix: God Mode lost after refresh / reconnect
--------------------------------------------------------

SYMPTOM
Joining as a God Mode spectator sometimes rendered the plain spectator view
(all seats as opponents, no revealed hand, no God Mode bar), typically right
after the "Reconnected successfully" toast.

ROOT CAUSES
1. The page-refresh auto-reconnect handler in public/main.js never applied
   res.isSpectator / res.isGodMode. A reload wipes the in-memory flags, so the
   client treated an acknowledged god spectator as a normal player and ignored
   the incoming god_hands payload.
2. roomManager.joinRoom() only matched a stored playerId when the seat was
   already flagged disconnected. On a fast refresh the browser reconnects before
   the server processes the old socket's disconnect, so the lookup missed and a
   brand-new spectator seat was minted with isGodMode = false.
3. The persisted session never recorded spectator/god status, so the reconnect
   could not re-announce the god password when a new seat was unavoidable.

FIXES
- Refresh reconnect now applies the server's isSpectator / isGodMode, enters the
  game for spectators (not just reconnected players), calls Game.applyGodView()
  after seating players, and reports god status in its toast.
- joinRoom() matches a supplied playerId regardless of connected state (holding
  the id is already the credential), so a refresh reuses the same seat with its
  god flag intact.
- Added persistSession() so roomCode/playerId/nickname plus isSpectator and
  isGodMode are stored together; the reconnect re-sends the god password.
- If a seat truly expired while the game runs, the reconnect now offers the
  spectate flow instead of dropping the user back to the lobby.

FILES TOUCHED
- public/main.js, server/roomManager.js, WORKLOG.txt


2026-08-05 — Fix: God Mode still lost on refresh + replaced prompt() entry
-------------------------------------------------------------------------

FURTHER ROOT CAUSES
4. The invite-link branch that runs on every page load rewrote uno_session from
   the URL query (?room&playerId&nickname) with no spectator/god fields. Because

- Replaced the prompt with a #spectate-modal dialog: "Watch as Spectator" vs a
  password field + "Enter God Mode". Wrong passwords show inline and keep the
  dialog open instead of silently downgrading; a warning toast fires if a
  password was supplied but God Mode was not granted.
- God Mode join toast now reads "God Mode active — every hand is revealed" so
  the granted mode is unambiguous.

2026-08-05 — God Mode: in-place upgrade, explicit Fine button, verified end to end

INVESTIGATION
Reported as "still broken after a hard refresh, and no Fine button in super

API for the god_fine / god_give_card handlers), so the report came from the

ROOT CAUSE FOUND
6. A spectator seat could never gain God Mode. joinRoom() reuses a seat by
   playerId before it looks at options.godPassword, so anyone who first watched

  supplied, and rejects a wrong one with an error instead of silently ignoring

  power is discoverable instead of hidden behind the canvas UNO diamond. The
  diamond still works and is now labelled FINE in God Mode.
- Added a 👁 unlock button shown only to spectators without God Mode. It reopens
  the spectate dialog in "upgrade" mode (password only, no "Watch as Spectator")
  and re-joins on the same seat, so a stuck plain spectator can unlock in place.
- Spectators no longer get dead controls: the UNO diamond is omitted for plain
  spectators and the pass/draw diamond for all spectators (their hit rects go
  away with them).
- The God Mode bar now renders even before a watched seat resolves, so the
  ◀ ▶ arrows can't disappear and leave the god with no way to switch seats.
- Removed a dead clearance variable in centerLayout() and corrected the
  misleading comment on the shared label baseline.

- Browser test (21 checks): god buttons visible for a god and hidden for players

2026-08-05 — Fix: stale service-worker cache hid every client change after deploy
--------------------------------------------------------------------------------

SYMPTOM
After deploying, the new God Mode buttons still did not appear — the in-game rail
showed only the emote and surrender buttons. Verified the live site was serving
the new markup and the new main.js, and that the running server answered the new
god_fine / god_give_card events, so the deploy itself was complete.

ROOT CAUSE
public/sw.js caches ?v= assets cache-first ("immutable by contract"), and none of
the ?v= numbers in index.html were bumped during this work. /play is served
no-store so the markup updated immediately, but the browser kept the old
main.js?v=48, renderer.js?v=41, game.js?v=39 and style.css?v=45 from the service
worker cache. The new buttons were therefore present in the DOM but no code
existed to reveal them, and a hard refresh could not help because a cache-first
service worker answers subresource requests from its own cache. This is the same
reason earlier rounds of fixes appeared to have no effect on the live site.

FIXES
- Bumped the asset versions: style.css 45 -> 46, renderer.js 41 -> 42,
  game.js 39 -> 40, main.js 48 -> 49.
- Bumped sw.js CACHE_VERSION uno-v48 -> uno-v49 and updated CORE_ASSETS to the
  new URLs, so the activate handler purges the previous cache.
- Registered the worker with updateViaCache:'none' so the worker script itself is
  never served from the HTTP cache, which is what let a stale worker keep pinning
  stale assets.

NOTE FOR FUTURE CHANGES
Any edit to main.js, game.js, renderer.js or style.css must bump that file's ?v=
number in index.html and CACHE_VERSION in sw.js, or returning visitors keep
running the old code.

VERIFICATION
- Every versioned URL returns 200 locally, the served /play references the new
  versions, and main.js?v=49 contains updateGodButtons and the new button ids.

FILES TOUCHED
- public/index.html, public/sw.js, public/main.js, WORKLOG.txt


2026-08-09 — Feature: per-room voice chat (WebRTC via LiveKit), God Mode included
---------------------------------------------------------------------------------

SUMMARY
Added optional voice chat scoped to each game room. Everyone seated at a table
can hear and talk to each other, and a God Mode spectator joins the same channel
so they hear the table and can speak back. Plain spectators are excluded. The
game's own traffic is unchanged — audio runs browser -> SFU and never passes
through the Node process.

WHY LIVEKIT AND NOT SOCKET.IO
Streaming microphone audio over socket.io is unusable in practice (latency,
bandwidth, mobile battery). Browsers expect WebRTC. A plain peer-to-peer mesh
would need every player connected to every other player, which collapses well
before the platform's 20-player room cap, so the design uses an SFU: each
client uploads once and the server fans the audio out.

SERVER
- New server/voice.js: wraps livekit-server-sdk. isConfigured(), voiceRoomName(),
  createToken() and removeParticipant(). LiveKit room name is "uno-<roomCode>",
  prefixed so a shared LiveKit deployment cannot collide with our room codes.
- Tokens are minted per request with a 3h TTL and identity = playerId, so a
  refresh replaces the old session instead of duplicating it. Grants are
  roomJoin/canPublish/canSubscribe with canPublishData disabled — game traffic
  stays on socket.io.
- server/index.js: new voice_token socket event. It verifies the caller is in
  the room it claims (socket.data.roomCode), then grants a token only to a
  seated non-bot player or a spectator with isGodMode. Plain spectators are
  refused. Rate limited to one token per 3s per connection.
- Kick, surrender and normal leave now also call voice.removeParticipant(), so
  a removed player is cut off from the audio immediately rather than talking
  until their token expires.
- Fully optional: with LIVEKIT_URL / LIVEKIT_API_KEY / LIVEKIT_API_SECRET unset
  the module logs "voice chat disabled" at boot and every token request returns
  enabled:false. Verified the server still boots clean with them unset.

CLIENT
- New public/voice.js (window.Voice): loads the livekit-client UMD build from
  jsDelivr lazily, only on the first join, so players who never use voice pay
  nothing. Handles connect/disconnect, mute, remote track attach/detach into a
  hidden audio host, active-speaker tracking, and browser autoplay unlocking
  (startAudio on the click that joined).
- Mic is published but muted on join. The permission prompt therefore fires on
  a deliberate click, and unmuting afterwards is instant. Denying the mic leaves
  the player connected in listen-only mode instead of failing the join.
- public/main.js: eligibility mirrors the server rule — God Mode, or holding a
  seat in the players list. Deliberately keyed off the seat rather than
  Game.isSpectator so an eliminated player keeps talking (they still hold a
  seat server-side). renderVoiceUI() is refreshed from showScreen(),
  renderPlayerList() and updateGodButtons().
- resetRoomState() now leaves voice, which covers leaving, surrendering and
  being kicked in one place — a live mic can never follow you to another table.

UI
- New 🎧 mic button on the right-hand rail (above the card-style button). Unlike
  its neighbours it is also visible in the waiting room, so its visibility is
  driven by a class from main.js instead of #game-screen.active. Icon states:
  🎧 join, ⏳ connecting, 🔇 in voice and muted, 🎙 live, 🚫 mic blocked,
  🔈 audio needs a tap. Live mic gets a green ring that pulses while speaking.
- New VOICE roster pill at the top of the screen listing everyone in the
  channel, with the speaker highlighted green and a ✕ to leave voice without
  leaving the game. Repositioned on narrow screens so it clears the ping chip,
  and rotated with the rest of the rail in landscape mode.

CACHE VERSIONS
- style.css 46 -> 47, main.js 49 -> 50, added voice.js?v=1.
- sw.js CACHE_VERSION uno-v49 -> uno-v50 and CORE_ASSETS updated to match,
  per the note left by the 2026-08-05 stale-cache entry.

DEPLOYMENT (Ubuntu VPS, self-hosted SFU)
DEPLOYMENT.md gained a Voice Chat section written specifically for a box that
already runs nginx on 80/443:
- Explicit warning NOT to use the official installer (curl get.livekit.io) or
  the livekit/generate cloud-init output. Both bundle Caddy and seize ports 80
  and 443, which nginx already owns for the game.
- Manual docker-compose install of livekit-server with network_mode: host, since
  NAT-mapping a 10,000-port UDP range through Docker is slow and unreliable.
- LiveKit's built-in TURN is used, so coturn is not required. TURN/TLS is on
  5349 rather than 443 to stay clear of nginx.
- Certbot for the livekit.<domain> subdomain, with the WHOLE /etc/letsencrypt
  tree mounted at the same path inside the container. Everything under live/ is
  a symlink to ../../archive/<domain>/fullchainN.pem, and that relative path
  only resolves if the directory sits at the same depth in the container as on
  the host. An earlier draft mounted live/<domain> at /etc/livekit/certs and
  archive at /etc/letsencrypt/archive; the symlink then resolved to
  /etc/archive/... which does not exist, and LiveKit crash-looped with
  "TURN tls cert required: ... no such file or directory". Hit for real during
  the first production deploy.
- A renewal deploy hook: LiveKit reads the TURN cert once at startup and would
  otherwise keep serving an expired one ~90 days in.
- Firewall rules (7881/tcp, 3478/udp, 5349/tcp, 50000-60000/udp and
  30000-40000/udp) plus a note that 7880 must stay closed since nginx reaches it
  on localhost. The TURN relay range (30000-40000 by default) is separate from
  the RTC media range and was missing from the first draft — leaving it closed
  makes voice work for most people and fail silently for anyone on a restrictive
  network, which is the worst kind of bug to diagnose later.
- turn.udp_port must be set explicitly or TURN listens on TLS only.
- A local dev-mode recipe (livekit-server --dev, devkey/secret, ws://localhost)
  for testing without a VPS or certificates, including the --node-ip flag that
  Docker Desktop requires (see below).

GOTCHA HIT DURING LOCAL TESTING
First local run failed with "ConnectionError: could not establish pc connection"
even though the signal channel connected and the logs showed the participant
joining the room. Cause: on Docker Desktop (Windows/macOS) containers run inside
a VM, so LiveKit advertised its internal Docker address as the ICE candidate and
the browser could not reach it. Publishing the ports is not enough — the
advertised address has to be reachable too. Fixed by passing --node-ip with the
host's LAN address; verify via docker logs showing "nodeIP" as the LAN address
rather than a 172.x one. Not an issue on Linux, where --network host is used.
- Cloudflare guidance, sizing, and a troubleshooting table.
The LIVEKIT_* variables were added to the environment variable list.

PRODUCTION ENVIRONMENT NOTES (discovered while writing the deploy steps)
- The live app runs on port 5000, not the 3000 the older parts of DEPLOYMENT.md
  assume. Added a callout above those nginx snippets so nobody copies them into
  a dead upstream.
- playunofree.com is proxied through Cloudflare (confirmed via the Server and
  CF-RAY response headers). The origin certificate only covers a leftover
  uno.draftly.co.in, which is invisible to visitors because Cloudflare
  re-terminates TLS, and implies the SSL/TLS mode is Full rather than
  Full (strict).
- That matters for voice: the livekit subdomain must be grey-clouded, since
  Cloudflare's proxy will not carry WebRTC media. Grey-clouding means the
  browser validates the ORIGIN certificate directly, so that subdomain needs a
  genuine Let's Encrypt cert — the main site's tolerance of a mismatched origin
  cert does not extend to it. Creating the record grey from the start also lets
  the HTTP-01 challenge reach the server without fighting the proxy.
- Documented the trade-off that a grey-clouded record publishes the origin IP.
  Unavoidable: WebRTC media needs a hostname resolving to the real server.

VERIFICATION
- livekit-server-sdk installed; token minting verified end to end — decoded JWT
  shows the expected room, identity and grants.
- node --check passes on all modified JS; no linter errors.
- Server boots with voice disabled and logs the expected message; /play serves
  voice.js and the new markup.

NOT INCLUDED
Voice for plain spectators, recording, push-to-talk, and a host toggle to
disable voice for a room.

2026-08-09 — UI change: voice status moved onto player names (roster pill removed)
-----------------------------------------------------------------------------------

SUMMARY
Replaced the separate VOICE roster pill with a mic indicator shown next to each
player's own name. Mic state is a property of a player, so it now lives with the
player instead of in a second list you had to cross-reference against the table.
The pill also covered the top of the board and duplicated names already on
screen.

WHERE THE INDICATOR APPEARS
- In game: painted onto the canvas seats, inside the existing name chip for top
  seats and beside the avatar for the side columns. Side-seat avatars shift left
  by half the icon width so the avatar+mic pair stays centred in the column.
- Waiting room: a .voice-pip span appended after each name in the player list.
  Bots never get one.
- Your own state stays on the 🎧 rail button as before, since you have no seat
  of your own on the board.

FOUR STATES, DELIBERATELY DISTINCT
- off      — nothing drawn at all. A table where nobody uses voice looks exactly
             as it did before this change; no empty icons, no wasted width.
- muted    — grey mic with a red slash.
- live     — white/green mic, unmuted but silent.
- speaking — green mic, glowing, with animated sound waves that breathe in time
             with the shared osc() so "talking" reads instantly at a glance.
Muted vs live is a colour AND a shape difference (the slash), not colour alone,
so it survives a colourblind viewer and a dim phone screen.

IMPLEMENTATION
- public/voice.js: new Voice.statusFor(identity) returning
  off | muted | live | speaking. Keyed on playerId, which is already the LiveKit
  identity, so no extra mapping is needed. Returns 'off' whenever voice is not
  connected, which is what makes the no-voice table render unchanged.
- public/renderer.js: new micPip() draws the glyph as vectors rather than an
  emoji — emoji mic/mute glyphs render differently per platform and cannot be
  recoloured per state. voiceStatusFor() wraps the global lookup so the renderer
  degrades to 'off' if voice.js has not loaded.
- The canvas already runs a continuous rAF loop, so speaking indicators update
  with no extra plumbing between the voice events and the board.
- public/main.js: makeVoicePip()/updateVoicePips() for the waiting-room list,
  driven by the existing Voice.onChange subscription.

LEAVING VOICE WITHOUT LEAVING THE GAME
The pill carried the ✕ that did this, so the gesture moved onto the mic button:
tap toggles mute, hold 600ms leaves voice. The click that follows a completed
hold is swallowed so leaving cannot also flip the mute state. The button title
advertises the gesture while connected.

KNOWN LIMITATION
A God Mode spectator has no seat on the board, so other players hear them
without seeing an indicator. Left as-is on purpose: showing one would reveal
that the room is being spectated, which defeats God Mode.

- sw.js CACHE_VERSION uno-v50 -> uno-v51.

- Server still boots with voice unconfigured.
- Grepped public/ for the removed ids and classes (voice-bar, voice-roster,
